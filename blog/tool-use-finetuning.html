Arc 7: Training & Post-Training

Tool-Use Fine-Tuning

7 min readbuilds on Supervised Fine-Tuning, Special Tokens, Chat Templates, and Input Formatting and Structured and Constrained Generation

A note on this series

I built this series as a learning project and used Claude extensively for research, drafting, critique, coding, and revision. I chose the curriculum and dependency order, drove the questions, edited the explanations, developed the interactive examples, and take responsibility for the published result.

This is an educational first edition rather than a formal reference. I am reviewing the articles against primary sources, testing the executable examples, and tracking corrections as the series matures. Some examples require specific hardware, model weights, or external services; they are teaching examples, not a tested deployment recipe.

This example serializes four messages: a user request, an assistant tool call, a tool result, and an assistant answer. Its SFT mask scores only assistant targets.

A prompt can demonstrate a tool-call format, yet a model may still invent a function, emit an argument with the wrong type, or add prose that breaks the parser.

Pretraining can include JSON, source code, and API calls, but that does not make a model reliable at choosing and using your tools. A useful training example connects the request, the available tool schema, the call, and the result.

Fine-tuning can improve those choices. Prompting supplies the available tools and task instructions; constrained decoding can enforce an output schema. Training, decoding, and caller-side validation address different parts of the problem.

Prerequisites

This post assumes you've read:

  • Supervised Fine-Tuning for how SFT reshapes a pretrained base model with (prompt, response) pairs, and the loss-masking convention where only response targets contribute directly to the loss.
  • Special Tokens and Chat Templates for how a multi-turn conversation gets flattened into one big token sequence with role markers.

The problem

Suppose you have a pretrained base model and a function:

get_weather(location: string) -> { temp_c: number, condition: string }

For “what’s the weather in Tokyo,” the expected call has this function name and these argument values:

{ "name": "get_weather", "args": { "location": "Tokyo" } }

Your caller needs a valid call with the right tool name and arguments. JSON whitespace and object-key order need not match this example. A different function name, an invalid argument, or extra prose outside the JSON can still break the contract.

Measure reliability on the tools and requests you intend to support. Separate syntax failures from incorrect tool choices, bad argument values, and unnecessary calls; one aggregate success rate hides useful information.

Passing these four checks is necessary but does not establish that the call answers the user’s request. A schema-valid weather lookup for the wrong city is still wrong.

What "training it" actually means

This post uses SFT for tool-call training. The loss and optimizer are the same as in the SFT recipe; the examples now include calls and tool results.

A plain SFT example is a (prompt, response) pair:

prompt: "Write a haiku about the sea."
response: "Silent tide breathes in..."

A tool-use SFT example can contain a full trajectory: the request, an assistant call, a tool result, and an assistant answer. The tokenizer’s chat template serializes these messages. In the assistant-only recipe here, assistant targets receive loss and user/tool targets are masked. Gradients can still flow through the representations of masked input tokens.

The call’s punctuation, field names, and argument values are part of the assistant output, as is its answer after reading the result. The real template determines which delimiters and end-of-turn markers also receive loss.

SFT increases the probability of the demonstrated calls. That can teach useful formatting and tool-selection patterns, but it does not guarantee valid JSON. A schema-aware decoder and a validator can still be useful at inference.

Tool results, the environment's reply, are also in the training sequence, because the model needs to condition on them to write the final answer. But they are not in MMM. You don't want the model's gradients to memorize tool outputs as if it had to generate them itself; you want the model to treat them as input it reads. Masking the tool-result tokens out of the loss is what draws that line.

A worked trajectory

The opening example contains four messages. Here is how they become a training sequence.

The user sends: "What's the weather in Tokyo?"

The full training example, in logical form:

system:     "You have access to a get_weather tool."
user:       "What's the weather in Tokyo?"
assistant:  <tool_call>{"name":"get_weather","args":{"location":"Tokyo"}}</tool_call>
tool:       {"temp_c": 18, "condition": "cloudy"}
assistant:  "It's 18 C and cloudy in Tokyo right now."

A real chat template determines the serialized role headers and termination markers. Llama 3-family formats distinguish message boundaries, final answers, and tool handoffs; a generic <tool_call> block is only schematic. Use the exact tokenizer and template for the checkpoint rather than assembling a plausible-looking string.

In this assistant-only recipe, the call’s JSON and the final answer supply target losses; system, user, and tool-result targets are masked. Whether assistant headers and particular delimiters are scored depends on the template and loader.

A model may generalize from these examples to unfamiliar tools described in context. Test that separately from performance on tools included in training; the number of examples required depends on the base model, tool schemas, and tasks.

Where the data comes from

Synthetic data is one source of trajectories, alongside authored examples and appropriately collected execution logs. The papers use different recipes: ToolAlpaca simulates tool interactions, while Toolformer samples candidate API calls, executes them, and filters by their effect on continuation loss. Toolformer is not simply a stronger teacher generating full chat trajectories.

Evaluate the teacher on the task. Inspect its tool selection, arguments, and use of results. A stronger general model is not automatically a reliable source of trajectories for a particular interface.

Execute or document the simulator. ToolLLM constructs trajectories with a catalog of real APIs. Whether results come from execution or simulation, check that the answer follows from them.

Validate before accepting. Parse the call, check its schema, inspect execution failures, and check that the final answer uses the returned result correctly.

Check coverage as well as volume. Include ambiguous requests, missing arguments, unavailable tools, execution failures, and requests that need no call.

Keep a held-out set of requests and tool schemas so the training run can be assessed on more than formatting.

Parallel tool calls

Some requests contain independent calls. Looking up the weather in three cities can run concurrently if no lookup depends on another’s result. By contrast, searching for an account and then fetching its records requires a dependency between calls.

A supported interface can let one assistant turn request several independent calls. Training examples can demonstrate that pattern. The runtime dispatches them concurrently and returns each result with its matching call ID.

Implementation sketch

Here is one logical training record, pretty-printed for readability. It uses an OpenAI-style message shape, not Llama’s native serialized token format. The custom loss_mask field requires loader support; it is not a standard training API field. Actual JSONL stores each record on one line.

A custom training loader applies the checkpoint’s chat template, locates assistant target spans, and builds labels with other targets ignored. Correct role boundaries and masking are part of the implementation; once those are established, the SFT loss applies.

In this OpenAI-style record, function.arguments is an escaped JSON string. Other loaders, including some Hugging Face chat-template interfaces, expect an argument object. Convert to the format your tokenizer and training loader actually accept.

Misconceptions

"Constrained decoding makes fine-tuning unnecessary." A correct grammar-constrained decoder can restrict completed outputs to valid syntax, subject to the supported grammar and termination handling. A truncated response may still be incomplete. Syntax constraints do not establish the correct tool, argument values, or need for a call. Prompting, training, decoding, and runtime validation address different parts of that problem; see Structured Generation.

"Fine-tuning teaches only the tools seen during training." A model can learn to read a new schema in context, but generalization needs evaluation. Conversely, it may invent a tool that was not supplied. Restrict dispatch to the application’s allowlist regardless of what the model emits.

"There is a fixed minimum dataset size." Data requirements depend on the starting model and the behavior being added. Use learning curves and held-out execution tests to decide whether more examples improve performance.

Additional reading (and watching)

  • Patil, S. G., et al. (2023). Gorilla: Large Language Model Connected with Massive APIs. arXiv:2305.15334. Evaluates API-call generation against documented tool interfaces.

  • Yan, F., et al. (2024). Berkeley Function Calling Leaderboard. UC Berkeley Gorilla team. The standing leaderboard for tool-calling reliability across models, with breakdowns by tool category and failure mode.

  • Schick, T., et al. (2023). Toolformer: Language Models Can Teach Themselves to Use Tools. NeurIPS 2023. The paper that crystallized the self-supervised recipe for tool-use training: insert candidate tool calls, execute them, keep the ones that reduce downstream loss.

  • Qin, Y., et al. (2023). ToolLLM: Facilitating Large Language Models to Master 16000+ Real-world APIs. arXiv:2307.16789. Demonstrates that fine-tuning generalizes to tools unseen at training time, given a sufficiently diverse catalog.

  • Tang, Q., et al. (2023). ToolAlpaca: Generalized Tool Learning for Language Models with 3000 Simulated Cases. arXiv:2306.05301. Describes a synthetic-trajectory pipeline in a simulated tool environment.

  • Zhou, C., et al. (2023). LIMA: Less Is More for Alignment. NeurIPS 2023. Studies a 65B model fine-tuned on 1,000 curated general instruction examples; it does not establish a tool-use sample requirement.

  • Anthropic. Tool use with Claude. Documents tool definitions, tool-use blocks, and tool-result messages for its API; these are not an exposed training-data contract.

  • OpenAI. Function calling. Documents Chat Completions tool-call IDs, JSON-encoded arguments, and matching tool-result messages. The record above uses that message shape with a custom loader field.

  • Meta AI. (2024). The Llama 3 Herd of Models. arXiv:2407.21783. Section on tool use describes the training mixture, the special tokens, and the zero-shot / few-shot evaluation protocol. The source for the public Llama 3 tool-use template.

  • Liu, X., et al. (2023). AgentBench: Evaluating LLMs as Agents. ICLR 2024. Broader agent evaluation that includes tool-use subtasks and has become a de facto reference for the "does the model actually complete the task" end of the reliability question.
