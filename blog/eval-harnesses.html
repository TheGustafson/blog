Arc 8: Evaluation & Scientific Discipline

Eval Harnesses: lm-eval-harness and HELM

5 min readbuilds on Loss vs. Benchmarks: Two Languages for Model Quality and Cross-Entropy, KL Divergence, and What Loss Functions Measure

A note on this series

I built this series as a learning project and used Claude extensively for research, drafting, critique, coding, and revision. I chose the curriculum and dependency order, drove the questions, edited the explanations, developed the interactive examples, and take responsibility for the published result.

This is an educational first edition rather than a formal reference. I am reviewing the articles against primary sources, testing the executable examples, and tracking corrections as the series matures. Some examples require specific hardware, model weights, or external services; they are teaching examples, not a tested deployment recipe.

Two evaluations of the same checkpoint can disagree because they asked different questions. One supplied five examples; another supplied none. One ranked answer strings; another generated an explanation and extracted a letter. Both may report “accuracy,” but that label does not make their procedures equivalent.

An evaluation harness makes the procedure explicit and repeatable. It loads items, renders prompts, calls a model, scores outputs, and aggregates results.

This builds on loss versus benchmarks and cross-entropy. We will use conditional log-probabilities to score candidate answers.

From a dataset item to a score

A task definition specifies the dataset and split, the prompt format, the allowed answers or generation settings, and the metric. Few-shot examples need their own selection rule. If an evaluation item appears among its own demonstrations, the result is no longer a held-out test of that item.

Save the rendered requests and per-item responses. A configuration file can look correct while the actual prompt duplicates a chat delimiter, loses an option through truncation, or presents an answer in the wrong place. Inspecting a few requests catches failures that an aggregate number conceals.

Record the model and tokenizer revisions, backend, precision, batch configuration, and seeds. Changes in services or numerical implementations can affect outputs even with temperature-zero generation.

Candidate likelihood and generated answers

s(a∣q)=∑t=1mlog⁡p(at∣q,a<t).s(a\mid q)=\sum_{t=1}^{m}\log p(a_t\mid q,a_{<t}).s(a∣q)=t=1∑m​logp(at​∣q,a<t​).

It selects the candidate with the largest score. Depending on the task, the candidates might be full answer strings or the letters A, B, C, and D after a prompt that already contains the options. Those are different conditional events. A multi-token answer needs the whole continuation scored, not just its first token.

Raw sequence likelihood tends to penalize additional tokens. Some tasks therefore use a normalization rule, but “normalized accuracy” is not one universal operation: inspect the task and implementation to see whether it divides by character count, token count, or another quantity. Changing that rule can change the winning answer.

Generation-based evaluation instead requests a response under a decoding policy and budget, then judges what came back. An exact matcher might accept a single answer string. A parser might extract a number or letter. Executable tasks may run tests. The parser is part of the measurement, including its handling of ambiguous or malformed answers.

Likelihood scoring can batch or cache candidate requests; it does not necessarily require a separate full forward pass per option. Generation also tests whether the model can produce an answer without supplied candidates.

Few-shot examples and templates

Few-shot examples can communicate an output format, teach a mapping, or suggest a procedure. They also change the context and consume its budget. Their effect depends on the examples, their order, the task, and the model. More examples are not guaranteed to help.

A template should match the model interface and the task. A base completion model and an instruction-tuned chat model may need different wrappers. For a controlled comparison, document that adaptation rather than silently treating all wrappers as interchangeable.

Prompt selection itself can overfit a benchmark. If you try twenty templates on the final test set and report the best, the score includes that selection process. Choose templates on development data and reserve a separate set for the reported comparison.

Using lm-evaluation-harness

EleutherAI’s LM Evaluation Harness supplies task definitions, model adapters, and scoring machinery. Pin the package or repository revision together with the model and dataset revisions. A task name alone does not freeze its implementation forever.

The current documented command interface uses lm-eval run. Older releases commonly use lm_eval without that subcommand; follow the documentation for the version you install.

The backend has to support the requests a task needs. A chat generation endpoint is not automatically a candidate-log-likelihood endpoint. Check adapter support before interpreting a missing metric or attempting to substitute generated text for unavailable probabilities.

Task YAML makes the intended behavior reviewable. This small custom task expects a local JSON Lines file containing question, choices, and a zero-based integer answer. It evaluates full option continuations with raw likelihood and uses no few-shot examples.

Keep this file alongside the data revision and rendered samples. The harness documentation describes how to register custom tasks and add generation filters, multiple references, or a different aggregation.

HELM and multiple measurements

Stanford’s HELM takes a broader approach to evaluation: define scenarios and report several relevant metrics under standardized conditions. The original work included accuracy, calibration, robustness, fairness, bias, toxicity, and efficiency where applicable. Those dimensions can reveal tradeoffs that one leaderboard column hides.

HELM is a family of evolving evaluations, so name the suite and version used. Do not assume that a result from one suite or adaptation can be compared directly with a superficially similar task elsewhere.

Reproducing a result

Begin with the exact checkpoint and reported configuration. Compare rendered prompts before spending a large inference budget. Check item counts, candidate strings, and answer extraction. Then compare per-item outputs; a batch of invalid generations suggests a different problem from a small set of genuine answer disagreements.

When differences remain, report them. A provider revision, unavailable training checkpoint, or omitted prompt template can prevent exact reproduction. That limitation belongs beside the score, rather than being concealed by rounding both results to the same percentage.

The next problem remains even with a perfectly reproduced procedure: did the model encounter the test material during training? That is the subject of contamination.
