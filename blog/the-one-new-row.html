Arc 5: Decoding & the Real Inference Algorithm

Why One New Token Means One New Row

14 min read

In the previous post I kept saying "decode is memory-bound" like it was an obvious fact. I showed the napkin math and the hardware specs, but I didn't really trace the matrix operations that make it true. The explanation is simple once you stare at the shapes.

The whole thing comes down to a single observation about the attention matrix. During training (or prefill), you compute the full lower triangle. During generation, you add exactly one new row at the bottom. That's the entire decode step, as far as attention is concerned.

Once this picture clicks, it changes how you think about autoregressive generation. So let me build it up piece by piece.

Prerequisites: You should be comfortable with attention as a matrix operation and causal masking. The prefill vs. decode post sets the stage for why decode is different, but I'll recap the key ideas here.

Full-sequence attention

Let's start from what we built in Post 4.1. You have a sequence of nnn tokens. Each gets projected into a query and a key, both of dimension dkd_kdk​. Stack them up:

Q=XWQ∈Rn×dk,K=XWK∈Rn×dkQ = X W_Q \in \mathbb{R}^{n \times d_k}, \quad K = X W_K \in \mathbb{R}^{n \times d_k}Q=XWQ​∈Rn×dk​,K=XWK​∈Rn×dk​

The attention score matrix is:

S=QK⊤∈Rn×nS = Q K^\top \in \mathbb{R}^{n \times n}S=QK⊤∈Rn×n

Every row is a query, every column is a key, and every entry SijS_{ij}Sij​ is the dot product between token iii's query and token jjj's key. With causal masking (Post 4.3), we zero out the upper triangle so no token can attend to future positions. But the computation still produces n(n+1)/2n(n+1)/2n(n+1)/2 entries in that lower triangle.

Then you multiply the softmaxed scores by V∈Rn×dvV \in \mathbb{R}^{n \times d_v}V∈Rn×dv​ to get the output: (n,n)×(n,dv)=(n,dv)(n, n) \times (n, d_v) = (n, d_v)(n,n)×(n,dv​)=(n,dv​). Every position gets a contextualized output vector.

This is what happens during training and during the prefill phase of inference. Big, fat matrix multiplies, the kind GPUs are built for, and hardware utilization stays high.

Now: generate one token

So what happens when we shift from processing a full sequence to generating a single new token?

At decode step ttt, you have exactly one new token. It produces a single query vector: qtq_tqt​ of shape (1,dk)(1, d_k)(1,dk​). But it needs to attend to all LLL prior keys (prompt tokens plus previously generated tokens). So KKK is (L,dk)(L, d_k)(L,dk​), sitting in the cache.

The attention computation becomes:

qtK⊤=(1,dk)×(dk,L)=(1,L)q_t K^\top = (1, d_k) \times (d_k, L) = (1, L)qt​K⊤=(1,dk​)×(dk​,L)=(1,L)

That's one row of scores, not a matrix multiply in any meaningful sense. It's a single dot product swept across LLL cached keys, producing an LLL-dimensional score vector. After softmax, you multiply by VVV:

(1,L)×(L,dv)=(1,dv)(1, L) \times (L, d_v) = (1, d_v)(1,L)×(L,dv​)=(1,dv​)

You get one output vector. That's it.

Each decode step adds exactly one new row to the attention matrix. Watch the dimension panel: Q is always (1, d_k) during decode.

The side panel makes the key point. During prefill, Q is (n,dk)(n, d_k)(n,dk​) and the score matrix is (n,n)(n, n)(n,n). During decode, Q is (1,dk)(1, d_k)(1,dk​) and the score matrix is (1,L)(1, L)(1,L). The shapes collapsed from a matrix to a vector.

And the previous rows? They sit in the KV cache, which is the subject of the next post. You never recompute them. You just grow the matrix by one row at a time.

The one new row, and what it costs

So the attention part of each decode step is cheap. One row, LLL dot products, done. But here's the thing: attention isn't even the bottleneck. The bottleneck is everything else in the forward pass. The weight-matrix multiplications that happen at every layer.

Here's the picture I want you to carry away from this whole post, and honestly from the whole arc. At every decode step, the model produces one new row of activations with shape (1,dmodel)(1, d_\text{model})(1,dmodel​). That single row has to pass through every layer: attention projections, attention output, feed-forward up-projection, feed-forward down-projection, output head. Each of those is a matmul of a (1,din)(1, d_\text{in})(1,din​) row against a (din,dout)(d_\text{in}, d_\text{out})(din​,dout​) weight matrix, producing another (1,dout)(1, d_\text{out})(1,dout​) row. One row in, one row out, and every weight in the matrix has to be read from memory to make it happen.

That's the handle: the one new row. I'll reuse this phrase across the next several posts. Any time you see it, it means: during decode, every layer does a vector-matrix multiply (not a matrix-matrix multiply), and the weight matrix has to be dragged from HBM to produce a single row of output.

One decode step, one weight matrix
(1, d_in) · (d_in, d_out) = (1, d_out)

A single activation row (top left, blue) times one weight matrix W. Watch the orange sweep: every column of W has to be read from memory to produce one cell of the output row. At the end of the sweep we've read every weight exactly once and done exactly one multiply-add per weight. The FLOPs/byte counter settles at roughly 1.

A quick convention note before the numbers: I'm counting each multiply-add as a single FLOP in this post to keep the sweep easy to follow. The standard convention in roofline analyses (and in the sibling posts training-vs-inference and prefill-vs-decode) treats a MAC as 2 FLOPs, which doubles all the arithmetic intensities below. Under that convention the single new row sits at ≈2\approx 2≈2 FLOPs/byte, prefill with a 2,048-token prompt at ≈4,096\approx 4{,}096≈4,096 FLOPs/byte, and the A100 ridge point is ≈156\approx 156≈156 FLOPs/byte. The ratio of decode AI to the ridge (and therefore the "less than 1% of peak" conclusion) is the same either way.

At each decode step, the model has to read its entire weight set from GPU memory to process that single token. For a 70B parameter model in fp16, that's about 140 GB of data flowing from HBM to the compute cores. And what do you get for all that data movement? Roughly 140 billion multiply-add operations. One multiply-add per parameter, per token.

The ratio of computation to data movement is called arithmetic intensity:

Arithmetic Intensity=FLOPsBytes read from memory\text{Arithmetic Intensity} = \frac{\text{FLOPs}}{\text{Bytes read from memory}}Arithmetic Intensity=Bytes read from memoryFLOPs​

For our single decode step:

AI≈140×109 FLOPs140×109 bytes=1 FLOP/byte\text{AI} \approx \frac{140 \times 10^9 \text{ FLOPs}}{140 \times 10^9 \text{ bytes}} = 1 \text{ FLOP/byte}AI≈140×109 bytes140×109 FLOPs​=1 FLOP/byte

One FLOP per byte. Compare that to prefill with a 2,048-token prompt, where you read the same 140 GB of weights but perform 2048×2048\times2048× more FLOPs. The arithmetic intensity jumps to roughly 2,048 FLOPs/byte.

That difference is the whole story. At 1 FLOP/byte, the GPU's compute cores are almost completely idle. An A100 can do 312 TFLOPS of fp16 math per second, but its memory bandwidth is only 2 TB/s. To keep those compute cores saturated, you'd need about 156 FLOPs/byte. During decode, you're running at 1. The GPU is operating at less than 1% of its peak compute capacity.

The roofline model

There's a classic visualization for this called the roofline model, from Williams, Waterman, and Patterson (2009). It's a 2D plot that makes the memory-vs-compute tradeoff immediately visible.

The x-axis is arithmetic intensity (FLOPs per byte, log scale). The y-axis is achievable performance (FLOPS/s). Your hardware imposes two ceilings: a sloped line from memory bandwidth on the left, and a flat compute ceiling on the right. Where they cross is the ridge point. Anything left of the ridge is memory-bound; anything right of it is compute-bound.

Roofline — NVIDIA A100 (FP16)
ridge at 156 FLOPs / byte

Decode at batch 1 lives way out on the left, sitting at 1 FLOP/byte under the orange (memory-bound) roof. The ridge point is at 156 FLOPs/byte. To make the GPU happy you have to climb that slope, which is what batching does. Prefill and training already live on the right side, hitting the green compute ceiling.

The whole arc 5 story can be read off this plot. Decode sits to the far left. Prefill and training sit to the right. Batching slides decode rightward up the slope. Quantization shifts the slope itself upward (fewer bytes per FLOP). And the workloads we're going to invent in later posts (speculative decoding, MQA, GQA) are all about getting decode closer to the ridge.

What does this look like in code?

The actual decode-step attention is surprisingly minimal.

Every dimension with a leading 1 is telling you the same thing: this is a vector operation, not a matrix operation. And the weight matrices (WQW_QWQ​, WKW_KWK​, WVW_VWV​, WOW_OWO​, plus the FFN weights) that are potentially billions of parameters? They all get read from memory just to produce that single vector.

Why this single fact is load-bearing

I keep coming back to the one-new-row picture because so many techniques in the inference stack are direct responses to it. Once you see them that way, most of Arc 5 and Arc 6 reduces to a single question: how do you push the ratio of FLOPs to bytes up from 1:1?

One root cause, four responses
all of Arc 5 on one page

The whole second half of Arc 5 fits on one page. Every technique either shrinks the bytes side of the ratio (KV cache, quantization) or grows the work side (continuous batching, speculative decoding). Same fraction, four different knobs.

The KV cache (Post 5.4): If you didn't cache the keys and values from previous steps, you'd have to recompute every prior token's projections at every step. The cache trades memory capacity for memory bandwidth, storing O(L)O(L)O(L) key-value pairs so you only do the new token's work.

Speculative decoding (Post 5.6): If each decode step wastes most of the GPU's compute (because it's memory-bound), why not use a small draft model to guess several tokens, then verify the guesses in one batched forward pass of the big model? You spend roughly the same bandwidth but potentially produce multiple accepted tokens.

Continuous batching (Post 5.7): If you're going to read all 140 GB of weights anyway, process multiple users' single-token decode steps at once. A batch of 32 users means you do 32 tokens' worth of math for the bandwidth cost of reading the weights once. Arithmetic intensity goes from 1 to 32 FLOPs/byte.

Quantization: Shrink the weights from fp16 to int4 and you cut the data volume by 4x. The FLOP count doesn't change, but the bytes you have to move do, so arithmetic intensity jumps from 1 to 4. You're still memory-bound, but the effective ceiling is 4x higher.

All of these exist because of the same root cause: at decode time, the attention matrix grows by one row, the model reads its entire weight set, and the result is a single vector.

Misconceptions

"The whole attention matrix is recomputed at each step." No. Only the new row is computed. The previous rows are exactly what they were before, and their key-value data sits in the cache. This is why the KV cache works: past attention patterns don't change when you add a new token (under causal masking, no existing token can attend to the new one).

"Decode is slow because attention is O(n^2)." During decode, the attention computation for the new token is O(L)O(L)O(L), not O(L2)O(L^2)O(L2). You compute one row of LLL dot products. The quadratic cost shows up during prefill (or training), where you compute the full n×nn \times nn×n matrix. The decode bottleneck is weight-reading, not attention.
