Why One New Token Means One New Row

Post 5.1 estimated the arithmetic intensity of batch-one decode. Here we'll trace the matrix operations behind that estimate.

During training or prefill, attention computes the full lower triangle. Each cached decode step computes one new row at the bottom.

Prerequisites: You should be comfortable with attention as a matrix operation and causal masking. Post 5.1 has the arithmetic intensity and roofline background, and prefill vs. decode sets the stage for why decode is its own phase.

Full-sequence attention

Let's start from what we built in Post 4.1. You have a sequence of nnn tokens. Each gets projected into a query and a key, both of dimension dkd_kdk​. Stack them up:

Q=XWQ∈Rn×dk,K=XWK∈Rn×dkQ = X W_Q \in \mathbb{R}^{n \times d_k}, \quad K = X W_K \in \mathbb{R}^{n \times d_k}Q=XWQ​∈Rn×dk​,K=XWK​∈Rn×dk​

The attention score matrix is:

S=QK⊤∈Rn×nS = Q K^\top \in \mathbb{R}^{n \times n}S=QK⊤∈Rn×n

Every row is a query, every column is a key, and every entry SijS_{ij}Sij​ is the dot product between token iii's query and token jjj's key. With causal masking (Post 4.3), we mask future-position logits with negative infinity before softmax, giving the upper triangle zero probability so no token can attend to future positions. But the computation still produces n(n+1)/2n(n+1)/2n(n+1)/2 entries in that lower triangle.

Then apply the scale and causal mask: A=softmax⁡(S/dk+M)A=\operatorname{softmax}(S/\sqrt{d_k}+M)A=softmax(S/dk​​+M). Multiply AAA by V∈Rn×dvV \in \mathbb{R}^{n \times d_v}V∈Rn×dv​ to get the output: (n,n)×(n,dv)=(n,dv)(n, n) \times (n, d_v) = (n, d_v)(n,n)×(n,dv​)=(n,dv​). Every position gets a contextualized output vector.

Training and prefill use these multi-row matrix products, which give the GPU more opportunities to reuse weights than a single-row decode step.

Now: generate one token

At decode step ttt, you have exactly one new token. It produces a single query vector: qtq_tqt​ of shape (1,dk)(1, d_k)(1,dk​). But it needs to attend to all LLL keys through the current position, including its own newly appended key. So KKK is (L,dk)(L, d_k)(L,dk​) after the append.

The attention computation becomes:

qtK⊤=(1,dk)×(dk,L)=(1,L)q_t K^\top = (1, d_k) \times (d_k, L) = (1, L)qt​K⊤=(1,dk​)×(dk​,L)=(1,L)

That's a matrix product with one output row, often described as a matrix–vector operation. It's a single dot product swept across LLL cached keys, producing an LLL-dimensional score vector. After softmax, you multiply by VVV:

(1,L)×(L,dv)=(1,dv)(1, L) \times (L, d_v) = (1, d_v)(1,L)×(L,dv​)=(1,dv​)

You get one output vector.

The one new row, and what it costs

At short contexts and small batches, reading the dense model's weights can dominate a decode step. Attention still reads O(L)O(L)O(L) cached keys and values per layer, so its bandwidth cost becomes substantial at long contexts or larger batches.

In batch-one decode, the model produces one new row of activations with shape (1,dmodel)(1, d_\text{model})(1,dmodel​). That single row has to pass through every layer: attention projections, attention output, feed-forward up-projection, feed-forward down-projection, output head. Each of those is a matmul of a (1,din)(1, d_\text{in})(1,din​) row against a (din,dout)(d_\text{in}, d_\text{out})(din​,dout​) weight matrix, producing another (1,dout)(1, d_\text{out})(1,dout​) row.

One decode step, one weight matrix
(1, d_in) · (d_in, d_out) = (1, d_out)

Follow the orange sweep across W: each column contributes one output coordinate. The counter uses one read per FP16 weight and one multiply-add per weight.

This is where the arithmetic intensity number from Post 5.1 comes from. Read every weight once, do one multiply-add per weight, and the ratio of FLOPs to bytes lands at roughly 1. That's what puts decode at the far-left end of the roofline plot, with a low bandwidth-limited ceiling in the simplified batch-one FP16 model. Large prefill and training matmuls can reach much higher utilization.

What this changes for inference

The following techniques change different costs in this decode step: repeated prefix computation, weight traffic, or the number of useful output rows per weight read.

The KV cache (Post 5.4): If you didn't cache the keys and values from previous steps, you'd have to recompute every prior token's projections at every step. The cache trades memory capacity and cache-read traffic for avoiding recomputation of earlier positions.

Speculative decoding (Post 5.6): If each decode step wastes most of the GPU's compute (because it's memory-bound), why not use a small draft model to guess several tokens, then verify the guesses in one batched forward pass of the big model? You spend roughly the same bandwidth but potentially produce multiple accepted tokens.

Continuous batching (Post 5.7): If you're going to read the model's entire weight set anyway, process multiple users' single-token decode steps at once. A batch of 32 users means you do 32 tokens' worth of math for the bandwidth cost of reading the weights once. Arithmetic intensity goes from 1 to 32 FLOPs/byte.

Quantization: FP16-to-INT4 packing reduces raw weight bytes by a factor of four. Scale metadata, packing overhead, and dequantization work affect the realized reduction. In the ideal weights-only model the arithmetic intensity rises from 1 to 4 FLOPs/byte; this is not a guaranteed fourfold speedup.

Misconceptions

"The whole attention matrix is recomputed at each step." No. Only the new row is computed. The previous rows are exactly what they were before, and their key-value data sits in the cache. This is why the KV cache works: past attention patterns don't change when you add a new token (under causal masking, no existing token can attend to the new one).

"Decode is slow because attention is O(n^2)." During decode, the attention computation for the new token is O(L)O(L)O(L), not O(L2)O(L^2)O(L2). You compute one row of LLL dot products. The quadratic cost shows up during prefill (or training), where you compute the full n×nn \times nn×n matrix. Which traffic dominates depends on context length, batch size, head sharing, and the model.
