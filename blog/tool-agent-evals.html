Arc 8: Evaluation & Scientific Discipline

Tool and Agent Evaluation

7 min readbuilds on Tool-Use Fine-Tuning and Evaluating Reasoning

A note on this series

I built this series as a learning project and used Claude extensively for research, drafting, critique, coding, and revision. I chose the curriculum and dependency order, drove the questions, edited the explanations, developed the interactive examples, and take responsibility for the published result.

This is an educational first edition rather than a formal reference. I am reviewing the articles against primary sources, testing the executable examples, and tracking corrections as the series matures. Some examples require specific hardware, model weights, or external services; they are teaching examples, not a tested deployment recipe.

An agent can write a convincing completion message while leaving the task unfinished. It can also take an unexpected route and still produce exactly the right result. Evaluating the message or matching a preferred action sequence will miss one of those cases.

Start with the state the task requires: a patch that passes the specified tests, a booking with the correct fields, or a document saved in the right place. Then keep the action trace to explain successes and failures.

This builds on tool-use training and evaluating reasoning. The model, its prompts, tools, environment, and stopping policy together form the system being tested.

Define success before running the agent

A coding task needs an initial repository state, a problem statement, and an evaluator. Specify which tests establish the requested change and which protect existing behavior.

SWE-bench uses real repository issues and evaluates submitted patches with tests. Its Verified subset contains 500 human-filtered tasks selected to improve evaluability. The public issues and code can still be encountered during training; task verification is not a contamination guarantee.

For transactional tasks, inspect the final database state and relevant policy constraints. The original τ\tauτ-bench evaluates simulated user interactions with domain tools and policies, including comparison of final database state against the annotated goal. A fluent conversation does not substitute for the required state change.

An evaluator should run even if the agent exhausts its budget, crashes, or never announces completion. Record those stopping conditions separately. Otherwise the reported denominator can quietly exclude the difficult runs.

Use the trace to locate failures

A trace can show that the agent read the right file, reproduced a failure, edited a relevant line, or interpreted a tool result incorrectly. These observations are useful for debugging even when the final task fails.

Avoid giving points simply for more actions. Repeatedly opening the same file should not increase progress. Define a small set of independently checkable milestones and count each at most once. Allow valid alternative routes rather than requiring a single reference trajectory.

A diagnostic milestone can also depend on the evaluator. “Ran tests” is easy to observe; “verified the fix” requires knowing that the relevant tests ran successfully against the final state. Keep that distinction in the labels.

The interval is center plus or minus half-width. Its center is not generally p^\hat pp^​. For six successes in ten attempts it is about 31.3% to 83.2%, which conveys how little ten runs establish.

Real tasks differ in difficulty, and trials on the same task share that difficulty. Pooling them as independent identical trials can understate uncertainty or answer the wrong question. Preserve task identifiers, compare systems on the same tasks, and use an analysis that respects the sampling design, such as resampling tasks rather than treating every repeated attempt as unrelated.

Two repeated-trial metrics ask opposite questions. pass@k counts whether at least one of kkk attempts succeeds. passk^kk, used by τ\tauτ-bench for reliability, asks whether all kkk succeed. Under the simple independent fixed-ppp model they are 1−(1−p)k1-(1-p)^k1−(1−p)k and pkp^kpk, respectively. Average per-task values when task success probabilities differ; applying either formula to an aggregate mean generally gives a different answer.

Control the environment, then record what remains variable

A fixed random seed does not reset a repository, database, browser session, clock, or external service. Save the starting state and reset it between runs. Record tool versions, timeout rules, retry behavior, permissions, and any network dependencies.

WebArena provides self-hosted websites for controlled browser tasks. In evaluations that instead use live services, record changes to those services as part of the measurement.

Deterministic-looking operations can still reveal hidden dependencies. A program that relies on the order returned by an unordered directory listing, for example, can behave differently across environments.

Compare quality under a budget

Report cost per attempt and latency together with success. Include failed attempts, tool usage, and any candidate selection. A cheaper unsuccessful run can look attractive if the report counts only its model tokens and omits the work needed to recover.

A system is Pareto dominated when another costs no more and succeeds at least as often, with a strict improvement in one of those dimensions. The example above assumes its numbers are known; real comparisons also need uncertainty and comparable cost accounting.

For identical independent restarts on one task, with success probability p>0p>0p>0, constant cost ccc per attempt, and a reliable way to recognize success, expected cost until the first success is c/pc/pc/p. Correlated retries, changing strategies, imperfect verification, and tasks with different ppp values change the interpretation. In particular, averaging ci/pic_i/p_ici​/pi​ across tasks is not the same as dividing mean cost by mean success probability.

For a human baseline, report participants’ expertise, tools, time budget, task selection, and success criterion. A human score under one protocol is neither a universal ceiling nor directly comparable to an agent allowed unlimited retries.

A minimal loop with an explicit evaluator

This sketch leaves the model and tools behind interfaces so the evaluation contract is visible. step returns a structured tool event or a finish event. The environment evaluator runs after either completion or budget exhaustion, and its result must be a boolean. Milestones come from trusted evaluation code, not from the agent’s self-report.

A malformed agent event is an execution error and still reaches final grading. A production harness also needs environment resets, timeouts, resource accounting, and durable traces. Evaluator failures should remain visible as evaluation errors, rather than being silently converted into successes or omitted from the report.

The human preference evaluation post turns to tasks where people’s judgments are part of the intended outcome.
