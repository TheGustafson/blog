Transcript Formats: How Providers Represent Tool Use

11 min readbuilds on Special Tokens, Chat Templates, and Input Formatting and Function Calling as Structured Generation

A note on this series

I built this series as a learning project and used Claude extensively for research, drafting, critique, coding, and revision. I chose the curriculum and dependency order, drove the questions, edited the explanations, developed the interactive examples, and take responsibility for the published result.

This is an educational first edition rather than a formal reference. I am reviewing the articles against primary sources, testing the executable examples, and tracking corrections as the series matures. Some examples require specific hardware, model weights, or external services; they are teaching examples, not a tested deployment recipe.

Providers encode tool exchanges differently. Anthropic uses content blocks. OpenAI Chat Completions uses a tool_calls field and a tool-role response message. Gemini uses functionCall and functionResponse parts. An adapter has to preserve the call and its matching result through those differences.

The wire formats differ, but a useful common structure is an ordered sequence of messages, tool calls, observations, and optional reasoning items. It does not make them interchangeable: preserving provider-specific fields is part of preserving the conversation.

The transcript carries control flow as well as text. Roles and content types tell the runtime what to execute and tell the model what kind of continuation it is receiving. Dropping that structure can change the next turn even when the visible words look unchanged.

The problem this layer solves

A text-only chat message can represent a request and an answer, but it does not identify an executable tool request or link a tool result to its originating call. An application can invent a text convention for that structure; a dedicated API representation makes the convention explicit.

ReAct-style traces used textual labels such as Thought:, Action:, and Observation:. A runtime parsing such output must decide how to handle malformed actions. Structured API fields move part of that parsing contract into the provider interface.

Prereqs

Two earlier topics provide the background. First, chat templates from arc 3: the provider-side JSON you send is not what the model sees. A chat template flattens structured messages down to a raw token stream, injecting special tokens like <|im_start|> or <|start_header_id|> that delimit roles. The transcript formats in this post are inputs to that rendering step; they are the structured side, not the token side.

Second, function calling from earlier in this arc: a model can return structured tool requests, with schema enforcement dependent on the API mode. What we're focused on now is how the resulting call, and the tool's response, are expressed in the next request you send.

The underlying structure

For text and tool exchanges, a common abstraction is:

Transcript=[ (role1,[block1,1,block1,2,…]),  (role2,[block2,1,…]),  … ]\text{Transcript} = [\,(\text{role}_1, [\text{block}_{1,1}, \text{block}_{1,2}, \ldots]),\ \ (\text{role}_2, [\text{block}_{2,1}, \ldots]),\ \ \ldots\,]Transcript=[(role1​,[block1,1​,block1,2​,…]),  (role2​,[block2,1​,…]),  …]

An ordered list of turns. Each turn has a role (user, assistant, sometimes system or tool). Each turn carries an ordered list of content blocks. A block is one of:

  • text — ordinary natural-language content.
  • tool call — "I want to run name with these arguments, under this id."
  • tool result — "Here is the output of the call with this id."
  • (optional) reasoning / thinking — private scratchpad that may or may not go back to the model on the next turn.

Every provider's format is some encoding of that list. Anthropic keeps blocks inside a content array on every message. OpenAI Chat Completions flattens most of it into fields on the message and promotes tool results to a separate tool-role message. Gemini renames blocks to "parts" and messages to {role, parts}. This toy exchange has corresponding calls and results across the three formats, while their full capabilities and validation rules differ.

What the SDK actually does with this

When you call client.messages.create or client.chat.completions.create or the Gemini equivalent, the SDK sends structured messages to the service. The service prepares the model input using its own formatting and multimodal processing.

The assistant doesn't "see" an Anthropic tool_use block or an OpenAI tool_calls array. It sees whatever tokens the provider's chat template chose to emit for that block (things like <|python_tag|> on Llama 3, <tool_call>…</tool_call> on ChatML-based models, or Harmony's channel-tagged segments on gpt-oss). The block structure is there so the service can render it correctly, and so the next turn can reference it by id.

When the model emits a tool call, what actually comes back from the inference engine is tokens. Those tokens get parsed by the provider into the structured block you see in the response. If the model's tokens are malformed (bad JSON in the arguments, a missing close-tag), the parse can fail in ways that are hard to debug from the SDK side. The provider is doing serialization in both directions, and the transcript format is the schema that serialization follows.

Scrub through a two-tool interaction built up one content block at a time. Anthropic style: tool_use blocks live in the assistant's content array, tool_result blocks live in the next user message, and the two are paired by matching ids.

Pair each result with its originating call using the provider’s rules. Anthropic and OpenAI use explicit call identifiers. Gemini also supports call IDs; preserve and echo them when returned. Older Gemini examples without IDs rely on the documented name/order convention. Missing or mismatched identifiers may be rejected by the API and must not be silently repaired by guessing.

The same turn in three formats

Here is the same exchange in each provider’s format: a user question, one tool call, its result, and the assistant’s answer.

Anthropic puts everything in a content array. A tool call is a block inside the assistant message; the tool result is a block inside the next user message, because Anthropic's format doesn't have a dedicated tool role at all.

OpenAI Chat Completions splits the same conversation across more messages. The assistant's tool call is a sibling field (tool_calls) on the assistant message, not a block inside content. The tool's response is its own message with a dedicated role: "tool" and a tool_call_id linking it back.

Gemini renames messages to contents, roles to user and model, and blocks to parts. Tool calls become functionCall parts inside the model's message. Tool results become functionResponse parts inside a user message. Gemini, like Anthropic, has no tool role.

An implementation sketch: normalize to the underlying shape

A normalizer can make a small text-and-tool example easier to inspect. The following is deliberately limited to the shown message shapes, not a lossless adapter: a production version must preserve thinking, signatures, images, unknown fields, and provider-specific metadata. The Gemini parser requires an ID supplied by the API or by an explicit pending-call matcher.

The Gemini parser refuses ambiguous matching rather than inventing an ID it cannot later recover. The Chat Completions parser must decode the arguments string because those arguments are JSON inside a JSON message.

To serialize in the other direction, define how call IDs and tool results map to each provider’s fields, including any reasoning state required for continuation.

Thinking, reasoning, and 2026's new twist

Reasoning APIs also represent state that may need to survive a tool turn. Providers differ in what they return and what the client must replay.

Anthropic added thinking and redacted_thinking blocks as first-class content types. On extended-thinking requests, the assistant message contains a thinking block before any user-visible text or tool calls. You pass those blocks back verbatim on the next turn when tools are in play. The model relies on its own reasoning being in context to pick up where it left off.

Gemini uses thoughtSignature: opaque encrypted reasoning-state data attached to response parts. Preserve the signature and its association with the original part when constructing the next request. It is not merely an ID pointing to a server-side scratchpad.

OpenAI Responses has explicit reasoning items and function-call items. You can continue stored state with previous_response_id, or manage history yourself and replay the required items. For stateless use, supported models can return encrypted reasoning content to carry forward. Harmony, used by gpt-oss, is a rendered token format with channels and recipients; it is a different layer from the Responses JSON API.

Each assistant utterance carries a channel (analysis / commentary / final) and tool calls are their own recipient-tagged message ending in <|call|>.

Chat Completions places tool calls in a field on the assistant message. Harmony makes them a distinct message with a recipient, and separates reasoning into its own channel. Both render the same logical turn; the boundaries live in different places.

Harmony documents token boundaries that the API schemas leave to the provider’s renderer. Its explicit channels and recipients make those boundaries available to inspect.

Misconceptions

"All three formats are equivalent, so it doesn't matter which you use." The formats encode the same logical object, but the encoding is not lossless in practice. Anthropic's tool_result can be a list of content blocks including images; OpenAI's tool message content is historically a string. A Gemini adapter that drops returned IDs or thought signatures can break a continuation. If you switch providers for the same agent without updating the transcript handling, you can get subtle misbehavior that's hard to trace to the transcript layer.

"The model sees the JSON I sent." No. The model sees tokens. The JSON is input to a chat-template step that renders structured messages down to a raw token stream with provider-specific special tokens. When Anthropic says the model "handles tool_use blocks natively," they mean the model was trained on token sequences that encoded tool_use blocks in a particular way, and the service prepares the corresponding model input. Your JSON and the model's prompt are related by a formatter, not by identity.

"Tool results come from the tool role." That is the Chat Completions convention. Anthropic puts tool results inside a user message with a tool_result block. Gemini does the same with a functionResponse part inside a user message. An adapter must use the destination API’s role and content conventions.

"You can skip the id field and the model will figure it out." Preserve the identifiers required by the API, even for one call. Missing or mismatched identifiers may cause request rejection or associate a result with the wrong request. Parallel calls make correct pairing especially important.

  • Google. (2025). Gemini API: Function calling. The functionCall and functionResponse parts inside contents, and the user/model role convention.
