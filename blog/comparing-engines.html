Runtime choices

High-throughput serving with paged cache management and iteration-level scheduling.

Check the installed version, model format, and hardware support before comparing performance.

An engine choice starts with a concrete deployment: a checkpoint, some hardware, and requests that must finish within a useful time. The engine has to support that combination before its benchmark numbers matter.

The preceding posts explain the parts of that decision: memory budgeting, quantization, parallelism, and scheduling. Here we use them to build a shortlist and a fair comparison.

What each project gives you

vLLM is a serving runtime built around batched execution and paged KV storage. Its model, hardware, and quantization support is broad, but support is a combination: a model working in BF16 does not establish that its chosen low-bit format works on your accelerator.

SGLang combines a serving runtime with radix prefix caching and interfaces for language-model programs.

TensorRT-LLM targets NVIDIA hardware. Older instructions centered on converting checkpoints and building TensorRT engines. NVIDIA's current documentation removes that backend in favor of the PyTorch execution backend, with AutoDeploy also using it. Check your installed release before following a build guide; the old workflow and the current one are materially different. TensorRT-LLM migration documentation.

llama.cpp runs GGUF models through CPU and several GPU backends. It is useful for local inference and also includes an HTTP server. Its backends differ in kernels and supported serving features.

Text Generation Inference (TGI) remains relevant to existing deployments, but its repository is archived and its README directs new work toward other runtimes. Maintenance is part of the comparison, even when an existing binary still runs successfully. TGI repository.

On Apple Silicon, include Apple's MLX as another local-inference candidate.

Compare supported combinations

Two engines may both support prefix caching while differing in eviction, request placement, and how much of your traffic actually hits the cache. Both may support structured output while accepting different schema features. “OpenAI-compatible” similarly describes an interface family, not a guarantee that every endpoint, streaming event, or request option is identical.

Keep model quality in the comparison. Changing the quantized checkpoint to make one engine run faster changes the experiment. Even with identical weights, floating-point kernels and sampling can produce different outputs; a shared architecture does not guarantee identical tokens.

A shortlist for a chatbot

Suppose a team has an eight-GPU NVIDIA node, a supported 70B checkpoint, and a chat workload with repeated system prompts. Its product budgets are p95 TTFT below 500 ms and p95 inter-token latency below 60 ms. Those are hypothetical requirements, not predictions for the hardware.

First check that each candidate supports the checkpoint's precision and the node's GPU generation. Then run the same request trace, with the same prefix-cache policy, on the surviving candidates. Record memory use, successful requests, tail latency, and aggregate output throughput. Tune each engine within the same resource limit and keep the resulting configurations.

The decision can then be concrete: one configuration may meet the latency budgets at more arrivals per second; another may be easier for this team to operate.

Keep the layers distinct

A platform can add authentication, routing, autoscaling, and deployment management around an engine. Some platforms support several engines or their own execution code. Avoid inferring a provider's internals from a familiar endpoint or a historical integration announcement.
