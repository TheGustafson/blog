Chat Templates and the Hidden Formatting Layer

16 min read

When you call a chat model, you hand it something like [{role: "user", content: "hi"}] and you get back a message. That feels like the whole protocol, but it isn't. Between the list of dictionaries you sent and the token stream the model actually sees, there's a layer that's easy to overlook, and the model was trained against the exact output of that layer. I call it the hidden formatting layer, and the goal of this post is to put it in your head so firmly that the next time an open-weight model underperforms for no obvious reason, you know which floor to look on.

The short version. A chat model is still a next-token predictor. user and assistant are not magic. To the network, they're just more tokens, wrapped in special tokens the model was trained to recognize as turn boundaries. A chat template is the function that takes your messages array and produces that token stream. Most open models ship their template as a Jinja string attached to the tokenizer, and the whole industry now calls the same thing with the same function name: tokenizer.apply_chat_template(messages).[^1]

The problem this layer solves

The models we call "chat models" are not, architecturally, chat models. They're the same decoder-only transformers from Arc 4, fine-tuned on a corpus where conversations have been laid out in a specific textual format. During training, the loss was computed against a flat string, not against a list of dicts. So at inference time, the input has to be in that same flat string, with the same special tokens in the same places, or the model is looking at something it has never seen.

The chat template is how we close that gap. It's the compiler from the API-level object (a messages array, the Arc 11 abstraction) to the token-level object (a sequence of integers, the Arc 3 abstraction). Two layers of the stack, bolted together by a Jinja string.

Here's the pattern I want you to keep: messages in, tokens out. That's the whole contract of the layer. Same function signature no matter whether you're calling GPT-4, Llama 3, Mistral, or gpt-oss. Only the innards of the function change.

Prereqs

This post sits pretty late in the series and leans on a few earlier pieces.

  • Tokenization and BPE from bpe-from-scratch. You know that a model never sees characters; it sees integer token IDs, and the tokenizer is the thing that turns one into the other.
  • Special tokens from special-tokens-chat-templates. You know that some token IDs don't correspond to any piece of normal text; they're reserved as structural markers the model learned to treat differently.
  • The training/inference split from Arc 5. You know the model's output is a distribution over the next token, and that training shaped that distribution on a specific textual format.

If "the model sees tokens, not JSON" is already instinct for you, you have the whole prereq.

The minimal formalism

A chat template is a Jinja template. That's the whole formalism. Jinja is a textual templating language with loops, conditionals, and variable interpolation,[^2] and the community converged on it because every framework already had it lying around.

Viewed as a function, a template is just:

template:messages→string\texttt{template}: \texttt{messages} \to \texttt{string}template:messages→string

The tokenizer then takes that string and turns it into token IDs. The two steps happen back-to-back inside apply_chat_template, but they're separable, and it's worth keeping them separate in your head. The template is where structure lives: role headers, turn delimiters, where the system prompt goes, how tool calls are serialized. The tokenizer is where bytes live, where "assistant" becomes a specific integer and <|eot_id|> becomes a reserved one.

Here's an annotated Llama-3-flavored template. Watch it cycle through the four structural moves every chat template is making.

A Jinja chat template · structural moves
{{ bos_token }}
{% for message in messages %}
  <|start_header_id|>{{ message['role'] }}<|end_header_id|>\n\n{{ message['content'] | trim }}<|eot_id|>
{% endfor %}
{% if add_generation_prompt %}
  <|start_header_id|>assistant<|end_header_id|>\n\n
{% endif %}

Drop the begin-of-text token once at the very start. Some models have it, some don't.

A chat template is a small Jinja program that loops over messages and emits role headers, content, and end-of-turn tokens. The `add_generation_prompt` clause at the bottom is what turns a scoring template into a prompting template.

The add_generation_prompt line is worth a second to appreciate. The same template is used for two different jobs: scoring a conversation (during training or eval, you want tokens for the assistant's actual words) and prompting a completion (at inference, you want to stop right before the assistant's turn so the model can continue from there). The flag flips which job you're doing.

apply_chat_template

Every major open-model tokenizer now ships with a chat_template field baked into tokenizer.json or tokenizer_config.json.[^1] Calling apply_chat_template(messages, add_generation_prompt=True) does three things: it runs the Jinja template to get a string, tokenizes that string, and returns you token IDs ready to feed into the model.

The important bit is that inference engines use the exact same template. vLLM and Text Generation Inference both expose a /v1/chat/completions endpoint that looks identical to OpenAI's, and internally they call into the tokenizer's template to do the messages-to-tokens compile before anything hits the GPU.[^3][^4] Which means the template isn't a Hugging Face convenience. It's the serving interface. When you deploy Llama 3 on vLLM and POST a messages array to it, the Jinja string shipped with the model weights is the thing that decides how your call becomes tokens.

You can override the template. You should almost never do that. The model was trained against one specific Jinja file, and the right default is to trust the file that came with the weights.

A few things worth calling out as it loops:

  • ChatML is the simplest. One open tag, one close tag, a newline, and the role name is just a plain token after the open tag.[^5] OpenAI used it internally in the original GPT-3.5-turbo rollout, and then Qwen, Mistral-Nemo, and many smaller open models adopted it. If you're guessing a template, guess ChatML.
  • Llama 3 uses header tokens (<|start_header_id|>…<|end_header_id|>) instead of a single open tag, plus a dedicated <|eot_id|> end-of-turn token and a once-per-sequence <|begin_of_text|>.[^6] Meta picked this design because it makes multi-turn boundaries unambiguous at the token level, even when role names are themselves tokenized weirdly.
  • Mistral inherits the [INST]…[/INST] bracketing from Llama 2.[^7][^8] There's no separate role header; the [INST] wraps both the system prompt and the user turn together, and the assistant's reply is the unbracketed text that follows. System and user are literally concatenated inside the same [INST] block.
  • Harmony is OpenAI's format for the o-series and gpt-oss.[^9] Same basic shape as ChatML but it adds a <|channel|> field on assistant turns (analysis, commentary, final), which is how reasoning and tool calls get structurally separated from the final answer.

Same conversation. Four different token streams. Four different models, each trained to recognize exactly one of them.

Why getting it wrong silently degrades

If you serve a model with the wrong template, nothing errors. The tokenizer is happy to tokenize any string. The model is happy to take any token sequence. It will produce coherent-looking output. You won't find out until you look at eval scores or your users start complaining that the model got worse.

Serving an open-weight model with a mismatched template doesn't throw. It just quietly drops eval scores by 20–40 points. The red bars grow in from zero to show the gap between the model's native template and a plausible-but-wrong one.

I call this silent degradation. It's a common failure mode of this layer, and it shows up in community writeups when a new open model lands. Mistral with a ChatML template, Llama 3 with the Llama 2 format, or gpt-oss with anything but Harmony will all run and produce coherent text. The numbers being reported are correct; what got measured is the template mismatch.

The mechanism is worth naming. The model learned its distribution over next tokens conditioned on a specific prefix shape. Role headers, end-of-turn tokens, system-prompt placement, all of that is part of the conditioning. When the prefix looks subtly different, the conditional distribution it produces is also different. The model isn't broken; it's correctly extrapolating from an input it was never trained on. Out-of-distribution in, out-of-distribution out.

What typically breaks first:

  • Tool calling. The structural tokens that mark a tool call (<tool_call>, <|python_tag|>, the Harmony <|call|> terminator) vary by family. Under the wrong template the model emits something that parses as text instead of as a tool call, and the whole agent loop stalls.
  • Refusals. Safety training is baked into the assistant turn's distribution. Change the scaffolding and you can drift into weirder refusal behavior, sometimes stricter, sometimes looser.
  • Instruction following. System-prompt influence is the most template-sensitive thing there is. If the template puts the system prompt in a different place (or folds it into the user turn like Mistral does), the model pays attention to it differently.

Tool calls live in the template too

One more place this bites. When you do tool_calls on an OpenAI-style API, the JSON you see at the API layer is one thing. What goes into the token stream is something else entirely, and the "something else" is chosen by the template. Here's the same call under a ChatML-style format and under Harmony.

One tool call · two template formats
ChatML-style (Qwen, Mistral-Nemo)
<|im_start|>assistant
<tool_call>
{"name": "get_weather",
 "arguments": {"location": "Tokyo"}}
</tool_call>
<|im_end|>
The tool call is a literal <tool_call>…</tool_call> XML-ish wrapper containing a JSON blob, still inside the assistant turn.
Harmony (gpt-oss, o-series)
<|start|>assistant
<|channel|>commentary
to=functions.get_weather
<|constrain|>json
<|message|>
{"location": "Tokyo"}
<|call|>
The tool call is its own commentary channel message with a recipient (to=functions.get_weather) and ends in <|call|> instead of <|end|>.

The same get_weather call comes out as an inline XML-ish wrapper under ChatML and as a recipient-tagged channel message ending in <|call|> under Harmony. A runtime that parses one format won't recognize the other.

This is why the inference engine has a tool-parser layer (--tool-call-parser in vLLM) whose job is to recognize the family-specific tool-call tokens and lift them back up into a structured tool_calls field.[^3] It's literally the inverse of the template: tokens in, messages out. When you hear someone say a model "supports tool use," some of what they mean is that this parser exists and works.

Misconceptions

"Chat templates are cosmetic, the model doesn't care about the exact bytes." The bytes are what the model was trained on, and swapping them out silently moves the inference distribution off of what the fine-tune covered. That's the mechanism behind most of the "this open-weight model isn't very good" reports that turn out to be template mismatches. The bytes are what it's predicting the continuation of. Two templates that look like they say the same thing to a human (system: you are helpful vs. <|im_start|>system\nyou are helpful<|im_end|>) are completely different prefixes from the model's point of view.

"I can invent my own template as long as it's consistent." You can't. Well, you can, but it'll be worse. The model saw a specific template during its fine-tuning. If you hand it a different one, even a more "elegant" one, you're feeding it out-of-distribution input. Every special token in the template was chosen because the training data used those exact bytes in those exact positions. Custom templates at inference time are a way to lose quality for free.

"The system prompt is always just a separate role at the top." In ChatML and Llama 3, yes. In Mistral's default template, the system prompt gets concatenated into the first user turn, because Mistral 7B v0.1 didn't have a dedicated system slot at all.[^7] In Gemma there's no system role; you're expected to put instructions in the first user turn. If you build abstractions assuming "there's always a system slot," you'll ship bugs against half the open-model ecosystem. Always check the template.

"The tokenizer and the chat template are separate things." In 2026, they aren't. Hugging Face made the call to ship the template as a field on the tokenizer so that the one object you load knows both how to split text into tokens and how to arrange messages into text.[^1] This means when you from_pretrained(model_name), you are already downloading the correct template. The whole workflow collapses to apply_chat_template, which is exactly the point of moving it there.

These ideas in the wild

Hugging Face apply_chat_template. Hugging Face added chat templates to transformers in October 2023, and by 2024 every major open model tokenizer ships one.[^1] The community standardized fast. The reason it worked is that there was no alternative that was cheaper to adopt.

vLLM and TGI serving stacks. vLLM's OpenAI-compatible server and Hugging Face's Text Generation Inference both use the model's shipped Jinja template to render incoming messages arrays into the model's native format before tokenization.[^3][^4] Both also support overriding the template via a CLI flag, which is mostly used for research or for models whose shipped template has a bug. The default path, and the right one, is to trust the template that came with the weights.

Harmony and channels. OpenAI's release of gpt-oss in 2025 came with a public spec for the Harmony transcript format, the first open example of a chat template that carries typed channels: analysis for reasoning, commentary for tool calls, final for user-facing output.[^9] This is how reasoning models keep their chain-of-thought separable from their answers at the token level. Watch for more families to adopt the channel idea. It's cheap and it solves a real problem that flat ChatML can't.

What's next

So. The hidden formatting layer is a Jinja template attached to the tokenizer that compiles your messages array into the token stream the model actually consumes. Every open model ships one. Getting it wrong doesn't throw, it just quietly makes the model worse. apply_chat_template is the portable way to call it, and every serving stack uses the same template under the hood.
