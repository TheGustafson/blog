Arc 11: Provider Ecosystems in Practice

Lock-In, Portability, and Abstraction Layers

20 min read

This is the last post of Arc 11. Every previous post in this arc zoomed into one provider and showed you what makes it weird. OpenAI's Responses API and the stateful previous_response_id model. Anthropic's content blocks and cache breakpoints and thinking blocks. Gemini's thought signatures and built-in grounding. Bedrock Converse. Hugging Face chat templates. Each of them is, individually, well-designed for the thing it is. Collectively, they do not form a coherent stack. They form a set of overlapping but subtly incompatible shapes that your code has to pick one of.

So the question this post is about: how portable is your code, actually, and at what cost?

I'm going to try to give you a mental model here that you can use to make the real decision, which is almost never "portable vs locked-in" as a binary. It is "what kind of optionality do I want, and what am I willing to pay for it?" That question has four reasonable answers, and this post is me trying to name them clearly so you can pick.

Prereqs

This sits at the end of Arc 11, so it leans on everything in the arc. If the names in the next few paragraphs don't ring bells, drop back to those posts first:

  • OpenAI Responses API: the stateful previous_response_id model and why it is not just chat completions with a new name.
  • Anthropic Messages and context tools: content blocks, cache_control, thinking blocks, disable_parallel_tool_use.
  • Gemini function calling and thought signatures: why Google's tool-use shape is its own thing.
  • Bedrock Converse: AWS's unified-across-models API that still leaves provider-specific fields as pass-throughs.
  • Hugging Face chat templates: how open-weights models encode the same content as the hosted providers, just with a Jinja template instead of an API shape.

And from earlier in the series, two things are load-bearing for this post: function calling as structured generation (the one universal thing at the bottom of all this is a JSON Schema) and the agent loop (the control flow that every provider has to support but shapes differently).

The minimal formalism: the intersection of features

Here's a way to think about portability that has held up for me. Every provider exposes a set of features. Call those sets SAS_ASA​ (Anthropic), SOS_OSO​ (OpenAI), SGS_GSG​ (Google), SMS_MSM​ (open weights). What your code can do without branching on the provider is the intersection:

Sportable=SA∩SO∩SG∩SMS_{\text{portable}} = S_A \cap S_O \cap S_G \cap S_MSportable​=SA​∩SO​∩SG​∩SM​

What LiteLLM or any unified shim gives you is the cheapest possible access to that intersection. It is not what any one provider is capable of. It is the floor across all of them.

Every feature not in the intersection becomes a choice. You either give it up, or you branch. Once you branch, the thing you bought with the shim, which was "my code doesn't know which provider it is talking to," is partly gone.

What the shim actually costs at request time

Adding a shim does a few things to your runtime shape that are easy to miss until production.

Latency. The shim itself is usually fast. LiteLLM is Python and does the translation in process. The real latency tax is provider routing: if you are using OpenRouter, you're adding a network hop between your code and the provider. Milliseconds, but measurable, and they stack up for high-QPS paths. For streaming the hop matters less, because you're blocking on model output anyway.

Observability. Your traces now go through one more layer. If something goes weird (a timeout, a schema validation error, a rate-limit bounce) you have to figure out whether the shim caused it, the provider caused it, or your prompt caused it. Most mature shims have decent logging, but you're now debugging across a boundary that wouldn't exist in the direct-SDK case.

Error shapes. Every provider has its own error taxonomy. Anthropic returns RateLimitError, OpenAI returns RateLimitError from a different class hierarchy, Gemini returns Google-API-style status objects. A shim normalizes these into one shape, which is wonderful until your retry logic was subtly depending on a provider-specific field and the normalization threw it away. The fix is the shim's exception_map, which is yet another surface you have to learn.

Cost tracking. This one is actually a win. A unified surface can attribute tokens-in and tokens-out across providers using a single pricing table. LiteLLM's cost callback is one of the more useful pieces of the abstraction, because every provider prices cache hits, cache writes, and reasoning tokens slightly differently and computing it yourself is a real chore.

The rule of thumb I keep in my head: a shim is close to free for simple chat calls and gets progressively more expensive in edge cases as you use more sophisticated features. The tax is proportional to how far you are from the intersection.

The portability spectrum

So. There are four reasonable places you can sit on this problem. Naming them clearly is half the point of this post.

The spectrum is not a quality axis. No tier is "better" than another. Each one buys a different kind of optionality at a different cost, and you want to pick the tier that matches your product's actual needs.

Raw provider SDK is the default if you're moving fast and you know which provider you want. You pay nothing, you get every feature the provider ships the day it ships, and your code is the simplest it can possibly be. The cost is that a swap is a rewrite. For a side project or an early-stage product, this is almost always the right answer. If Anthropic ships a new thinking-block feature on Tuesday, you can use it on Tuesday.

Thin adapter over SDKs is the tier that fits most production code that might, someday, need to change providers. You define a ChatProvider protocol, you implement it against one SDK today, and you leave the door open for a second implementation. The adapter is yours, which means you can pass through exactly the provider-specific features you care about and abstract exactly the ones you want abstracted. It's work, but it's the work of a week, not a quarter. We'll do this in the code widget below.

LiteLLM or OpenRouter is the tier where you trade feature depth for breadth. You get 100+ providers for the cost of learning one API, and the maintained shim handles auth, retries, fallbacks, cost tracking, and normalization of the common surface. This is the right tier if your product is not deeply model-specific, or if you want the ability to fall over from one provider to another in real time when one of them has a bad day.

Model gateway or router is the production tier. Portkey, Braintrust, or an internal proxy. Now you have a service in the path that handles routing rules, budgets, caching, PII redaction, audit logs, per-team rate limits, and A/B traffic shaping between models. This is what you graduate to when you have a real org using LLMs, because it centralizes the policy decisions that would otherwise be smeared across a hundred services.

I want to flag one thing that's easy to miss: the tiers compose. You can run a gateway that internally uses LiteLLM as its shim, and expose a thin adapter on top of that to your application code. That stack works. What matters is that you know which layer is responsible for what, so when something breaks you know which layer to debug.

The worked example: three shapes for the same call

Let me make the abstraction thing concrete. Here is the same request (an assistant turn with a tool available, asked to look up the weather in Paris) in three shapes.

Raw Anthropic SDK. Messages have a structured content list. Tools are declared with JSON schemas. The response is content blocks.

Raw OpenAI SDK. Messages are flat strings (or a typed content list in the newer shape). Tools live under tools with a wrapper {type: "function", function: {...}}. The response returns tool_calls on the choice.

LiteLLM. One completion() call. The tool schema matches the OpenAI shape, which LiteLLM uses as its internal lingua franca and translates on the way out to whichever provider you name.

Same logical request, same logical tool. Three different code surfaces, three different sets of features you can reach.

Notice what's identical across all three: the JSON schema for get_weather. That schema is the same object in every version, character for character. That's not an accident. JSON Schema is the lingua franca, the one layer every provider genuinely agrees on. Anthropic calls it input_schema, OpenAI calls it parameters, LiteLLM wraps it in OpenAI's envelope, but the schema itself is portable. When I'm designing tools for a new system, I write the JSON Schemas first, in a file that doesn't know about any provider, and everything else adapts around them.

Now look at what you can't express identically. Anthropic's cache_control breakpoint on a tool definition, so you cache the schema between turns: that's a field on the tool object that only Anthropic understands. OpenAI's strict: true for structured outputs: an OpenAI-only flag. Gemini's grounding config: absent from both. LiteLLM will let you pass these through as provider-specific kwargs, which is excellent, but the moment you use one your call is no longer portable. You've made a choice.

Your code depends on the protocol, not on any SDK. Each adapter translates the shared interface into one provider's shape. The pulse runs down a different lane each cycle.

The adapter pattern in the diagram above is what "tier 2" looks like in practice. Your application code knows only about the protocol (chat(messages, tools) → Response). Each adapter is a small class that translates the protocol call into whatever shape that SDK wants. When you need provider-specific features, you add an optional parameter to the protocol (cache_breakpoints, thinking_budget, grounding), and each adapter chooses to use it or ignore it. Your code is portable on the protocol and explicitly branchy on the extensions, which is honest.

Implementation sketch

Here's a sketch of what the provider-interface pattern looks like in about forty lines, compared side-by-side with the one-line LiteLLM version. Both make the same call, return a normalized response, and support the basics. The adapter version buys you control; the LiteLLM version buys you breadth. Pick deliberately.

The adapter version is more code, but the code is yours. When Anthropic ships a new feature you want to use, you add one field to extra and one line to AnthropicProvider.chat. The LiteLLM version is shorter, covers many more providers out of the box, and is a great default when your product is not deeply model-specific. Both are legitimate. The question is which set of trade-offs fits what you're building.

Evals as optionality insurance. The reason most "portable" codebases can't actually change providers without pain is that they can't measure whether the change broke anything. Having a shim is the cheap part. Having a regression suite rich enough to tell you "swapping to GPT loses 7 points on tool-use correctness but gains 3 on JSON adherence" is the expensive part. And it's the part that actually makes a swap survivable.

If you take one thing from this post, take this: the shim isn't the portability. The eval coverage is.

When lock-in is fine

Everything above was about optionality. But I want to be clear that choosing to lock in is a legitimate move, not a failure.

If extended thinking is 30% of what makes your product good, you are choosing Anthropic. That is a real decision, and pretending otherwise by wrapping it in a shim that can't express thinking doesn't make you portable; it makes you worse at the thing you picked Anthropic for. Same with computer use. Same with Gemini-grade long-context recall. Same with strict structured outputs if that's how your tool-chain is wired.

The honest mental move is to notice which features are actually load-bearing for your product and separate them from features that are merely convenient. The load-bearing ones lock you in, and you pay for that with a dependency on one vendor's roadmap. The merely convenient ones are where portability investments pay off, because the cost of swapping is low enough that the optionality is cheap.

I'd rather ship something locked in on one load-bearing feature and portable on everything else, than something nominally portable everywhere and mediocre everywhere too.

Misconceptions

"Use LiteLLM and you're portable." You are portable on the features LiteLLM exposes, which is roughly the intersection of what the major providers agree on. That intersection is large enough to be useful and small enough to matter. Every feature you use via LiteLLM's pass-through kwargs (cache_control, thinking, strict) is a provider-specific branch in your code with a LiteLLM-shaped syntax in front of it. That's fine. It's just not what "portable" usually connotes. The right frame is: LiteLLM makes the portable parts cheap, which frees your budget to handle the non-portable parts deliberately.

"An abstraction layer solves provider risk." It solves API-surface risk, not quality risk. If the new provider is worse at your task, the shim cannot help you. If the new provider's safety tuning refuses prompts the old provider handled, the shim cannot help you. If the new provider's tool-calling model hallucinates arguments differently, the shim cannot help you. A shim buys you the ability to send the same request to a different model. Whether that model is any good for your product is an eval question, not an abstraction question.

"OpenAI-compatible means interoperable." A lot of providers now ship OpenAI-compatible endpoints, and it's a real convenience. But "OpenAI-compatible" is a shape, not a capability. Implementing the endpoint doesn't mean implementing every feature (streaming tool-call deltas, strict mode, reasoning effort, logprobs, response_format), and the implementations differ in corner cases. Treat "OpenAI-compatible" as "roughly the same shape, test the corners" rather than "drop-in replacement."

"Provider-agnostic code is always the goal." Sometimes it's the right goal. When it is, you pick tier 2 or tier 3 and live with the tradeoffs. When it isn't (early product, small team, one load-bearing feature) it's fine to sit on tier 1, use the raw SDK, and revisit the decision later. "Portable" isn't free. It has a cost, and you should only pay that cost when the optionality is worth more.

Additional reading (and watching)

  • BerriAI. (2023–2026). LiteLLM. Open-source Python library providing a unified completion() interface across 100+ LLM providers, plus retries, fallbacks, cost tracking, and a gateway mode. The de facto shim for multi-provider Python applications.
  • OpenRouter. (2023–2026). OpenRouter Documentation. A hosted API that exposes hundreds of models behind a single OpenAI-compatible endpoint, with live pricing, provider routing, and automatic fallbacks.
  • Chip Huyen. (2024). AI Engineering. O'Reilly. Chapter 10 ("Inference Optimization") and the provider-management discussions throughout cover exactly the portability trade-offs this post names, from a systems-engineering perspective.
  • Portkey. (2024–2026). Portkey AI Gateway. A production gateway that sits between applications and LLM providers, adding routing, caching, virtual keys, guardrails, and observability. The canonical commercial tier-4 product.
  • Braintrust. (2024–2026). Braintrust Proxy. Eval-oriented LLM platform with a proxy layer that supports model routing, caching, and integration with evaluation runs. Nearby niche to Portkey with different emphasis.
  • JSON Schema Working Group. (2020). JSON Schema Specification, Draft 2020-12. The schema language that every major LLM provider's function-calling / tool-use API accepts as input for tool parameter definitions. The one genuine point of agreement across providers.
  • vLLM Project. (2023–2026). vLLM OpenAI-compatible server. Shows the community-default shape for exposing open-weights models behind an OpenAI-compatible API, which is why tier-3 shims can treat local and hosted models uniformly.
  • Eugene Yan. (2023–2025). Patterns for Building LLM-based Systems & Products. Practitioner-facing essays on the architectural patterns that show up repeatedly in production LLM systems, including the evaluation-driven development pattern that underlies the "evals as optionality insurance" idea.
