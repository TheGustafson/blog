A note on this series

I chose the curriculum and dependency order, drove the questions, edited the explanations, developed the interactive examples, and take responsibility for the published result.

This is an educational first edition rather than a formal reference. Some examples require specific hardware, model weights, or external services; they are teaching examples, not a tested deployment recipe.

A serving benchmark is useful when it predicts what happens to your requests. A high token rate on short, repeated prompts does not tell you whether a long coding prompt will interrupt an active chat stream.

Start with a question you can test: how much traffic can this deployment serve while meeting its latency budgets? Then keep enough detail to reproduce the answer.

Name the measurements

Time to first token (TTFT) measures the interval from a specified start point to the first generated token. Client-observed TTFT includes network and front-end work as well as queuing and prefill. Server-side TTFT may use different boundaries; label them.

Inter-token latency (ITL) is the sequence of gaps between generated tokens. Time per output token (TPOT) is usually a per-request average over the decode interval. For G>1G>1G>1 output tokens, a common definition is

TPOT=end latency−TTFTG−1.\mathrm{TPOT}=\frac{\mathrm{end\ latency}-\mathrm{TTFT}}{G-1}.TPOT=G−1end latency−TTFT​.

The average does not reveal an isolated long stall. Keep token-gap tails and per-request averages separate, and state whether end latency includes the final protocol event.

End-to-end latency is the time to the final output. When the boundaries match, it is TTFT plus the sum of the remaining token gaps. There are G−1G-1G−1 such gaps, not GGG.

Output throughput is completed output tokens divided by elapsed wall-clock time. Report whether it covers a device, a node, or the entire deployment. If an eight-GPU tensor-parallel replica generates 800 tokens/s in total, its normalized rate is 100 tokens/s/GPU, not 800. Input-plus-output throughput is a different metric and must be named separately.

Report the mean, median, and relevant tail percentiles alongside sample counts and failures. Means are useful for aggregate accounting; they cannot stand in for tail latency.

A streaming HTTP event is not necessarily one model token. It may contain only a role field, several tokens, usage data, or a finish marker. A client that increments a token counter for every event and timestamps the first event as TTFT can report convincing but incorrect numbers. Inspect the protocol and the benchmark's counting method.

Make the workload representative

Record prompt and output length distributions, request arrival times, generation settings, and prefix sharing. Also retain content where it affects execution: prefix hits depend on actual token identity; speculative acceptance, MoE routing, early stopping, and constrained decoding can depend on the text.

Long prompts deserve explicit coverage. Dense attention still has quadratic arithmetic even when FlashAttention avoids storing the complete score matrix in HBM.

Use both controlled synthetic inputs and a representative trace. Synthetic cases isolate a change; trace replay tests whether that change helps the workload you intend to serve. Keep prefix caching conditions explicit so a warm repeated prompt is not compared against a cold unique one.

Sweep load, and count good results

A closed-loop concurrency sweep keeps up to a fixed number of requests outstanding. Each completion makes room for another. This is useful for exploring saturation, but slower responses automatically reduce the offered arrival rate.

An open-loop test schedules arrivals independently of completions. It can expose a growing queue that a closed-loop test hides. Replay realistic bursts or use a documented arrival process, and ensure the client can sustain it. Distinguish time waiting in a client-side semaphore from time waiting at the server.

For interactive traffic, measure the request rate that meets both TTFT and streaming-latency requirements. Goodput counts successful work meeting the chosen budgets. A failed, timed-out, or truncated request must not silently disappear from the denominator. Leave operating headroom for variability rather than deploying exactly at one observed threshold.

Control the measurement conditions

Warm up the execution paths you intend to measure, and record the warmup policy. Compilation, graph capture, and allocation may affect initial requests. Separately measure startup or cache-miss behavior if it matters to the product; “warm” is not automatically more representative.

Use the model's tokenizer and chat template. Confirm whether reported counts include prompt tokens, special tokens, or speculative drafts. Pin the checkpoint revision, quantization configuration, engine version, drivers, hardware topology, power settings, and sharing/isolation policy.

A few hundred requests may characterize a median while providing very few observations near p99. Repeat runs, report variability, and use enough duration and samples for the tail you care about.

A reproducible starting command

vLLM provides an online benchmark CLI with workload and load-pattern controls. Use the CLI belonging to the installed release; flags and supported datasets can change. Its benchmark guide explains the metric boundaries and arrival controls.

This example requires checkpoint access and suitable hardware. It leaves synthetic length defaults to the installed release, so record those defaults or set them explicitly before comparing runs. It is a smoke measurement, not a production capacity result. Extend it with a documented length distribution, warmup, arrival-rate sweep, and saved detailed records.

Convert achieved throughput into cost

Suppose a complete deployment costs an assumed $2/hour and sustains an assumed 1,800 output tokens/s over the billed interval. Its compute-only cost is

23600×1800×106≈$0.31\frac{2}{3600\times1800}\times10^6\approx\$0.313600×18002​×106≈$0.31

per million output tokens. These inputs are hypothetical, not a current GPU rental quote or a measured Llama result.

Use an achieved rate over the same interval as the cost. If you instead start from a peak saturated rate, account for idle time separately; do not apply an extra utilization factor to a rate that already includes it. Host memory, networking, storage, replicas, and other operating costs may belong in the final budget.

An increase in concurrency at the latency threshold lowers cost per token only if successful throughput rises relative to provisioned cost. Report both alongside the workload and latency measurements.
