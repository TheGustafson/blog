Arc 11: Provider Ecosystems in Practice

Bedrock, Azure AI, and Cloud Model Marketplaces

19 min read

The previous posts in this arc walked through the three big provider APIs in their natural form: OpenAI Responses, Anthropic Messages, Google's Gemini API. Direct contracts, direct billing, direct credentials. That is how a startup ships a feature on Friday.

That is not how a bank ships the same feature. The moment a real enterprise wants to put a model into production, the question stops being "which API is nicest" and starts being something like: who has signed our DPA, whose audit logs land in the same SIEM as everything else, who supports private connectivity from our VPC, whose IAM lines up with the identities our employees already have. The answer to most of those questions, for most large companies in 2026, is the cloud they already pay. So the model gets bought through AWS, or Azure, or GCP, with the model vendor sitting one layer behind the bill.

That is what a cloud model marketplace is. AWS Bedrock, Azure AI Foundry (the rebrand of Azure AI Studio in late 2024), Vertex AI Model Garden.[^1][^2][^3] Same idea every time: one IAM surface, one paper trail, one network boundary, many models behind it. This post is about what that abstraction actually does, where it leaks, and how to think about the cost of going through it.

Enterprise can't sign N contracts

Imagine you are the platform team at a 50,000-person company. The product orgs want Claude. The data science team wants Llama. The customer-support team likes GPT-4o. Marketing wants to try Mistral. Five teams, four models, four direct contracts, four sets of API keys floating around in five places, four bills going to four different cost centers, four security reviews, four data-processing addenda, and four sets of audit logs that nobody can correlate.

You can survive this for a while. Then somebody asks, in writing, which of those four providers your customer data has been sent to in the last 90 days, broken down by user. If the answer is anything other than a query against a single audit table, you have a problem.

The marketplace is the answer to that. One contract with the cloud, one IAM surface, one network policy, one log destination. The model vendors sit one hop behind, and the cloud provider has already done the legal and compliance work to put them there. You consume them through one SDK with one set of credentials. The trade you make for that simplicity is real, and the rest of the post is about exactly what it costs.

Prereqs

This post sits late in the series. It assumes you already have:

  • The three direct provider APIs from the earlier posts in this arc: OpenAI, Anthropic, Google. You know what messages, tools, and a streaming response look like in each.
  • Function calling as structured generation. The marketplaces all expose tool calling, and the nuances we'll see come from how each one normalizes the schema.
  • Transcript formats. When we look at where the abstraction leaks, the leaks live in the gaps between these formats.

You don't need to know any AWS or Azure specifics. Where I drop a service name, I'll say what it does inline.

What sits in the box

A cloud marketplace is doing more than proxying requests. The product is the layered stack between your code and the model weights. The actual model is the bottom of that stack and, in some sense, the least interesting part of it.

Every layer between your code and the model weights is something the cloud provider owns. That ownership is the whole product. It is also where most of the latency, the cost markup, and the leaks live.

The layers between your application and the model are what you're actually buying. The provider model is the floor; everything above it is the marketplace.

A few of those layers deserve a name.

IAM and identity. Bedrock requests are signed with AWS SigV4 against an IAM principal. Azure AI requests carry an Entra ID token. Vertex requests use a Workload Identity Federation token or a service account. Whatever the cloud already uses for everything else, the model API uses the same thing. This is plumbing, and it's most of why these products exist at all: a separate API-key system would sit outside the identity stack the rest of the company already runs against.

Private connectivity. Bedrock has VPC Endpoints (PrivateLink), Azure has Private Endpoints, Vertex has Private Service Connect. The same idea everywhere: traffic to the model doesn't traverse the public internet, and the model service appears as a private IP inside your network. For workloads with that requirement, the direct provider APIs don't offer an equivalent.

Guardrails and content safety. Bedrock Guardrails, Azure AI Content Safety, Vertex safety filters.[^4][^5] These are pre- and post-generation classifiers that can block PII, redact sensitive topics, or refuse denied subjects. They're configured once at the marketplace level and apply to every model behind it, which consolidates policy into one surface.

Audit and logging. Every request lands in CloudTrail / Azure Monitor / Cloud Audit Logs by default, alongside the rest of your cloud's audit stream. Same query language, same retention policies, same export pipelines. The 90-day "who did we send what to" question becomes a SQL query against a single log table.

Managed retrieval. Bedrock Knowledge Bases, Azure AI Search integration in Foundry, Vertex AI Search and the RAG Engine.[^6] Take a bucket of documents, get back a retrieval API. We covered the shape of RAG architectures earlier; the marketplace versions are opinionated implementations of that shape with the embedding model, vector store, and retrieval orchestration wired together up front.

Agent runtimes. Agents for Bedrock, Azure AI Agent Service, Vertex AI Agent Builder. The same agent loop we covered in tool loops, wrapped in a managed runtime so you don't run the loop yourself. We'll come back to this in the next post.

The model itself is the last of these. It's the part with the most marketing attention, and, for the platform team writing the check, the part whose selection comes after everything above it is settled.

The Converse API: one shape, many backends

If a marketplace is going to sit between you and many models, it has to take a position on what the request body looks like. Each provider has its own messages shape, its own tool-calling format, its own knobs for things like temperature and max tokens. Either the marketplace forwards all of that verbatim and forces you to learn N native formats, or it picks a canonical shape and translates.

AWS picked the second, and they call it the Converse API.[^7] You send a single, normalized request (messages, system, toolConfig, inferenceConfig) and Bedrock rewrites it into whatever the model on the other end actually expects. Same call shape for Anthropic, Llama, Mistral, Cohere, Amazon Nova. Azure has a parallel construct in the Azure AI Inference SDK that targets the OpenAI Chat Completions shape across non-OpenAI models. Vertex's chat methods do the same thing for Gemini and partner models in Model Garden.

The minimal Converse shape is small enough to write down:

request={ modelId, messages, system, toolConfig, inferenceConfig }\text{request} = \{\, \texttt{modelId},\, \texttt{messages},\, \texttt{system},\, \texttt{toolConfig},\, \texttt{inferenceConfig}\,\}request={modelId,messages,system,toolConfig,inferenceConfig} response={ output, stopReason, usage, metrics }\text{response} = \{\, \texttt{output},\, \texttt{stopReason},\, \texttt{usage},\, \texttt{metrics}\,\}response={output,stopReason,usage,metrics}

messages is a list of role-tagged content blocks (text, image, tool use, tool result). toolConfig is a list of JSON-schema tool definitions plus an optional toolChoice. stopReason tells you whether the model stopped on end_turn, tool_use, max_tokens, or stop_sequence. If you have read the function-calling post and seen the Anthropic Messages API, this should look familiar. Converse is essentially Anthropic's shape, generalized.

What the marketplace does for you is the rewrite. Here is what a single Converse request actually becomes when it hits each backend.

Field names rename (modelId → model, maxTokens → max_tokens). Anthropic-specific features (extended thinking, prompt caching) are not exposed by Converse and have to be requested via Bedrock's separate InvokeModel API with the raw Anthropic body.

Same canonical request, three native rewrites. The fields rename, drop, or get bolted on differently for each model family. The rewrite is the whole product of Converse.

Two things to notice.

The translations on the right are not always lossless. For Anthropic, Converse rewrites cleanly because Anthropic was the design template. For Llama, Converse has to apply the chat template and synthesize a tool-call protocol on top of an LLM that doesn't natively emit tool_use blocks. For Nova, Converse is nearly the identity but provider-specific knobs sneak in via additionalModelRequestFields, the official escape hatch.

That escape hatch is the whole story of why unified APIs leak. Every model has features the others don't. The unified API has to either expose them awkwardly, hide them entirely, or punt to a side-door.

Why the abstraction leaks

Here is the durable handle from this post. Every provider has unique capabilities; any unified surface either drops them or mirrors them awkwardly. Call this why the abstraction leaks. The other side of the same coin is the marketplace tax: what you give up, in features and sometimes dollars, in exchange for the unified surface.

The clearest way to see it is a feature matrix.

What the unified marketplace surface actually exposes in 2026. Direct-only means the feature exists for the model but is only reachable via the raw provider-specific API.

A few things this matrix surfaces.

Anthropic's extended thinking is reachable on Bedrock, but only via Bedrock's lower-level InvokeModel call with the raw Anthropic body. Converse doesn't expose it. So the moment your application wants reasoning tokens, you fall off the unified surface and start writing Anthropic-shaped JSON inside your AWS SDK call. You are back to provider-specific code, just with AWS auth and audit on top of it.

Prompt caching is GA on Bedrock for Anthropic and Nova, but the breakpoint controls are constrained relative to what the direct Anthropic API gives you. Azure OpenAI does prompt caching automatically with no breakpoint controls at all, which is more user-friendly but less surgical. Vertex caching is a separate first-class API. Three providers, three different mental models for the same idea.

Open-weight models are where the leaks get the most visible. Llama on Bedrock has tool calling because Converse synthesizes it through prompting, but the reliability of the tool-call schema is going to drift from what you'd see on a vendor that shipped tool calling natively. If you swap a model id from anthropic.claude-... to meta.llama-... in your Converse call, your tool-call success rate can move noticeably even though the request body didn't change. Same surface, different physics underneath.

The way I think about it: the marketplace gives you portability across models for the cheap-and-common features, and forces you back to provider-specific code for the cutting-edge ones. That's not a flaw of the marketplaces. It's a structural consequence of trying to put one face on N moving products.

What it costs

Two costs are worth measuring separately: dollars per token, and milliseconds per request.

On dollars, the rule of thumb is that closed-source models price the same on the marketplace as on the vendor's own API, because the cloud is reselling capacity rather than running the inference. Open-weight models carry a real markup on the marketplaces because the cloud is doing the inference itself.

The Llama row is the one to sit with. The price difference there is not a markup the cloud is charging on top of Meta (Meta doesn't sell hosted Llama). It is the price of the cloud running the GPUs for you, with a managed endpoint, autoscaling, and the rest of the marketplace stack underneath. If you compare Bedrock Llama to a self-hosted vLLM deployment on the same cloud, you'll find the marketplace number is reasonable for what it includes. If you compare it to a tuned vendor like Together or Fireworks, you're paying real money for the audit trail.

Most of the marketplace overhead is the guardrail evaluation, which runs on both the input and the streamed output. It is not a huge tax per request, but it is there on every request, and it is the price of an audit trail you can hand to a regulator.

Latency decomposition for one small request. The marketplace adds an auth check, an input guardrail pass, a logging write, and an output guardrail pass. The model's own time-to-first-token is essentially the same.

Read the bars carefully. The model's TTFT is essentially identical between the two paths, because it is the same model. What changes is everything around it: SigV4 instead of an API key, an input guardrail pass on the prompt, an audit log write per call, an output guardrail pass on the streamed response. Roughly 200ms of overhead per request for what amounts to compliance you can hand to a regulator. Whether that is a fair trade depends entirely on whether you have a regulator.

Worked example

Here is the same get_weather tool call on Claude, written first against the Anthropic direct API and then against Bedrock Converse, side by side. This is the place to feel the rewrite.

The Anthropic call is one positional messages argument and one tools list. The Converse call is the same information, just renamed and re-nested: system becomes a list of text blocks, tools becomes toolConfig.tools[].toolSpec, input_schema becomes inputSchema.json, max_tokens becomes inferenceConfig.maxTokens, the user message content becomes a list of typed blocks. Same model on the other end. Same answer in the response, with the same stop_reason: "tool_use" semantics.

What changed:

  • Auth. The Anthropic call reads an API key from the environment. The Bedrock call resolves an IAM principal via boto3's credential chain (env vars, instance profile, SSO, etc.) and the request is SigV4-signed.
  • Region. Bedrock requests are bound to a region. Anthropic's API has no region knob.
  • Audit. The Bedrock call lands in CloudTrail with the IAM principal, request id, and model id. The Anthropic call lands in Anthropic's logs, which you can read but which don't sit in your existing observability stack.
  • What you can't ask for. Extended thinking, prompt caching breakpoints with the full granularity Anthropic offers, the citation feature. None of these are reachable via Converse. You'd drop down to bedrock.invoke_model with a raw Anthropic-shaped body, at which point you're writing Anthropic code inside an AWS SDK call.

That last point is the thing to remember. The Converse API doesn't replace the Anthropic API. It overlays a normalized common subset on top of it. The full feature surface is still under there; you just have to leave the abstraction to reach it.

Misconceptions

"Bedrock is just a proxy to Anthropic, use whichever is cheaper." This was my first mental model, and it's wrong on a few axes. The pricing for closed models is essentially identical, so "cheaper" is the wrong comparison. Bedrock and the direct Anthropic API have different rate limits, different model availability windows (new Claude releases tend to land on the Anthropic API first by days or weeks), different region footprints, and different feature surfaces. They run on different inference fleets, so even latency distributions differ. They are two distinct products that happen to serve the same model weights. The right question is not "which is cheaper" but "which set of constraints does my team need."

"The unified API means I can swap models freely." For the basic features, sort of. You can swap Claude for Llama in a Converse call without changing the request body. You can not swap them and get equivalent behavior. Tool-call reliability, JSON-schema adherence, instruction following, refusal patterns, context length, even the stop tokens are different per model. A model swap is a re-eval, every time. Converse buys you the right to do the re-eval without rewriting the SDK code, which is real value, but it is not "swap freely."

"If I'm not in a regulated industry, I should skip the marketplace." Usually true, but not always. If you're a four-person startup, the direct APIs are obviously simpler. If you're a 200-person company that already runs everything on AWS and pays your bill in committed-use discounts, going through Bedrock means one fewer vendor relationship and one fewer set of credentials, and the IAM integration is genuinely worth something even without a compliance officer asking for it. The better question is how much your existing cloud relationship is already giving you, and whether the marginal vendor-management cost is worth eliminating.

"Azure OpenAI is the same product as OpenAI." Same model weights, different product. Azure OpenAI runs in your Azure tenant, billed against your enterprise agreement, with Entra ID auth and Azure Monitor logs. The API surface is almost the same: different endpoint, different model id format ("deployments" instead of model names), different fine-tuning pipeline, sometimes a release lag for new model versions. Code that works against api.openai.com does not work unmodified against your Azure OpenAI deployment, and you'll notice the differences on the first migration.[^8]

In the wild

Bedrock Knowledge Bases. The clearest example of the marketplace selling a layer above the model. You hand Bedrock an S3 bucket of documents, point it at a vector store (OpenSearch Serverless, Aurora, Pinecone), and pick an embedding model. The RetrieveAndGenerate API takes a question, runs retrieval, calls Claude (or whichever model id you pick), and returns a grounded answer with citations. The whole RAG architecture from arc 9 is implemented for you, with the catch that you implement it Bedrock's way or not at all.[^6]

Azure AI Foundry's Model Catalog. Azure positions Foundry as a "model garden plus tooling" rather than a pure inference marketplace. The catalog spans OpenAI models (via Azure OpenAI Service), Meta's Llama family, Mistral, Cohere, Phi, and a long tail of open-weight models deployed as managed endpoints. The Azure AI Inference SDK gives you a unified call shape across most of them, leaning on the OpenAI Chat Completions shape as the canonical form.[^2]

Vertex AI Model Garden. The third pole. Strong on Gemini (obviously), strong on partner models (Anthropic Claude has been in Model Garden since 2024), strong on the open ecosystem (Llama, Mistral, Gemma, Stable Diffusion). The integration with BigQuery and Vertex AI Search is the differentiator if your data already lives in GCP.[^3]

Snowflake Cortex and Databricks Mosaic AI. A different shape of marketplace, domain-specialized rather than general-purpose. Cortex Functions let you call models directly from a SQL query against the table the model is supposed to reason about (SELECT SNOWFLAKE.CORTEX.COMPLETE('claude-...', text) FROM ...).[^9] Databricks Mosaic AI Model Serving exposes a similar set of foundation models behind Databricks' workspace IAM, with first-class hooks into MLflow and Unity Catalog.[^10] Both are niche compared to the big three, but they're the right answer if your data and your model need to live in the same governance perimeter.
